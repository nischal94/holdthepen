## Original Plan State
# Design — Agent-mediated claim: an accessible WebMCP reference application

Date: 2026-09-01 (rev 2, after external review)
Deadline: 2026-09-03 13:00 PT (2026-09-04 01:30 IST)
Status: awaiting approval

## 1. Thesis

The WebMCP spec's Accessibility considerations section is empty, and open
community issues (#65, #272, #277) are actively discussing what a user agent
must guarantee when an agent acts inside a page on a person's behalf. Issue
#277 — an open proposal, not endorsed spec direction — describes review,
attribution, correction, and approval requirements for consequential actions,
citing WCAG 2.2 error prevention for legal and financial data.

We ship a working exploration of those unresolved mediation requirements, in
the domain where the stakes are self-evident: a consequential public-service
form.

**The product claim:** "We demonstrate how WebMCP can make complex,
consequential forms easier to understand and complete while preserving visible
attribution, correction, and review."

**Not the claim:** "We solved secure human-only submission." The page can
constrain its WebMCP contract; it cannot know whether an ordinary UI click came
from a human. That missing primitive — a trustworthy human-only approval
boundary — is the spec gap this project demonstrates. Per OpenAI's Site Tools
documentation, an agent with no suitable WebMCP tool may still use regular
browser capabilities; removing a tool constrains the declared interface, it
does not prove human presence.

Non-thesis: we are NOT claiming WebMCP replaces or duplicates assistive
technology. Issue #91 (closed) settled that the layers are separate. The agent
is an intermediary; the accessibility work is in the mediation UI.

## 2. What we are building

**Wendell County Household Support Allowance** — a fictional benefits claim,
positioned as an **accessible reference application**: it demonstrates how
consequential public-service forms can expose safe, reviewable WebMCP
workflows. Invented county, invented programme, invented branding. No real
agency depicted or implied. The README states explicitly what is simulated
(submission, eligibility rules, identity) and what a real form operator could
reuse (the tool surface, the provenance model, the review flow).

**Four sections, one document** (see §4):

1. Household
2. Income
3. Disability or caring responsibilities
4. Declaration and review

Content requirements across the four sections: at least one conditional branch,
one genuinely confusing term, one validation failure path, and the full
agent-fill → human-review → correct/undo → approve arc.

### The three-way split

| Layer | Actor | Rule |
|---|---|---|
| Understand | Agent | Read-only. Unlimited. No confirmation needed. |
| Fill | Agent | Writes to visible fields. Always attributed. Always undoable. |
| Decide | Human only, in the visible UI | No WebMCP tool commits the claim. |

### The differentiating feature: consequence explanation

Real public-service forms contain questions narrower than they appear (income
*received* vs income *earned*). `explain_answer_consequences` explains what the
question actually asks, distinguishes commonly-confused concepts, and shows how
each truthful answer affects the (fictional) workflow. It never recommends a
strategically advantageous answer; it encourages correction when the person is
uncertain. This is the concrete answer to "what can people and agents do
together that was difficult or impossible before": comprehension, not typing.

## 3. Tool surface

Imperative API only. Top-level document only. No iframes. No declarative
forms. Reason: ChatGPT's in-app browser supports neither declarative tools nor
iframe-registered tools; the Chrome/ChatGPT intersection is imperative +
top-level.

Nine tools. Names are ASCII alphanumeric plus `_` `-` `.`, under 30 characters.

### Read-only (annotations.readOnlyHint: true)

| Tool | Purpose |
|---|---|
| `get_claim_state` | Current section, completion, empty fields, agent-filled-and-unreviewed fields. |
| `explain_question` | Plain-language explanation of one question: what it means, why it is asked. |
| `define_term` | Define one piece of bureaucratic jargon plainly. |
| `explain_answer_consequences` | What the question actually asks; distinguish confusable concepts; how each truthful answer affects the workflow. Never recommends an answer. |
| `review_agent_entries` | Every agent-supplied value, its source, and review status. |

### Write (annotations.readOnlyHint: false)

| Tool | Purpose |
|---|---|
| `fill_field` | Write one field. Marks it agent-supplied, unreviewed. Returns the validator's verdict. |
| `clear_field` | Undo one field. |
| `goto_section` | Move the visible form and focus to a section. |

### The staged-review tool

| Tool | Purpose |
|---|---|
| `prepare_submission_review` | Does NOT submit. Stages a submission review in the UI and returns a structured summary of what would be sent and what it commits the claimant to, or the list of missing required fields. Execution then ends. |

This is staging, not elicitation. True elicitation would pause the tool, collect
the human's answer, and resume. The current draft spec has no
`requestUserInteraction()` (an older proposal did). Because standardized
elicitation is absent, the tool stages review and returns; after the human acts,
the agent must observe the updated state via `get_claim_state` in a separate
turn. The README documents this as the missing primitive, referencing #165.

There is deliberately no commit tool in the WebMCP surface. Final approval is a
UI control. This demonstrates the intended human-review pattern; it is not a
browser-enforced human-presence guarantee (see §1 and §9).

## 4. Architecture

**Single document. No route-per-step.** Sections conditionally rendered in one
page; the URL never changes during the claim. Rationale: issue #255 documents
agents failing to re-find tools after navigation/server roundtrips
(sdras/webmcp-server-interaction-demo); the React hook's unmount-unregisters
behaviour corroborates it.

**Tools registered once, in a persistent client layout component.** Never
per-section; registered for the life of the page.

**Never unregister to signal unavailability** (#262). Unavailable tools stay
registered and return a descriptive error.

**Defensive API access everywhere:**
`const mc = document.modelContext ?? navigator.modelContext;`

**Always await registration with .catch().** `registerTool()` rejects on
duplicate/empty name, empty description, non-function execute, non-serializable
schema; unawaited, the tool silently does not exist.

**State**: one React reducer holding field values, per-field provenance
(`human` | `agent`), reviewed flag, validation state. No backend, no database,
no auth.

**Persistence**: memory by default. An explicit "Save draft on this device"
control writes to sessionStorage; a visible "Clear claim data" control wipes
it. No silent localStorage. The UI never implies data is securely stored.

**Stack**: Next.js App Router, TypeScript, Tailwind. Deployed on Vercel.

### Accessibility mechanics (the deliverable)

Exploring #277's requirements 4 and 5:

- An agent write fires an `aria-live="polite"` announcement naming the field
  and that it was updated by the agent and needs review — **never the value
  itself** (speech output must not disclose personal or financial data to
  bystanders). The person inspects values deliberately in the field or queue.
- Agent-supplied values carry a persistent, non-colour-dependent marker: a
  text badge ("filled by agent — not yet reviewed") exposed via
  `aria-describedby`, not merely an outline.
- A keyboard-reachable review queue lists agent entries with Accept / Correct /
  Clear per entry; the same list is enumerable via `review_agent_entries`.
- Per-field undo, announced.
- The submission review states in text exactly what would be committed.
- Nothing relies on colour, animation, or visual focus alone.

## 5. Error handling

- Tool failures return descriptive text so the model can self-correct and
  retry ("validate strictly in code, loosely in schema").
- `fill_field` on an unknown field returns the valid field names.
- `prepare_submission_review` with missing required fields returns which.
- If `document.modelContext` is absent: a banner with exact setup instructions
  (Chrome 149+ flag, or the ChatGPT desktop app). The form still works by hand.
- Tool outputs under 1.5K chars; descriptions under 500; param descriptions
  under 150.

Deploy verification FIRST:

2. Deploy to Vercel; get the live URL.

`Origin-Agent-Cluster: ?1` set affirmatively in next.config. No
`Permissions-Policy` header (a restrictive allowlist omitting `tools` would
silently disable registration).

### Behavioral test suite (MANDATORY — WebMCP Leverage is the tie-breaker)

Shipped in the repo as eval scenarios (Chrome `expectedCall` format where
applicable, plus a manual checklist):

1. Explain a question without modifying state.
2. Fill one valid field.
3. Reject an unknown field with a helpful error.
4. Handle a validation failure and retry with corrected input.
5. List all unreviewed agent entries.
6. Prepare submission with missing fields → returns the missing list.
7. Prepare submission when complete → returns staged summary, does not commit.
8. Confirm no WebMCP tool can commit the claim (tool-surface audit).

## 7. Threat model (scoped)

- **In scope, mitigated**: agent overwriting human-entered values (provenance +
  review queue + undo); agent committing the claim via the tool surface (no
  commit tool exists); silent agent edits (announcements + persistent badges);
  data disclosure via speech (values never announced); data lingering in the
  browser (memory-first, explicit save/clear).
- **Out of scope, documented**: an agent actuating the visible submit button
  via generic browser automation — the page cannot distinguish this from a
  human click; this is the missing platform primitive the README names.
  Prompt injection into the agent from page content (we set
  `untrustedContentHint` where applicable and keep outputs terse, but agent-side
  defenses are the agent's responsibility).

cryptographic human-presence proof.
